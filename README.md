## OpenCode в GitHub

Начните новый комментарий в issue, обсуждении PR или у строки diff с `/oc` или `/opencode` и напишите запрос через пробел. Например, `/oc explain this issue` попросит агента объяснить задачу. Чтобы получить спецификацию по обсуждению, укажите скилл явно: `/oc запусти скилл to-spec по обсуждению этого issue`.

На чистом раннере агент прочитал файл трекера `docs/agents/issue-tracker.md` и скиллы `to-spec`, `to-tickets` и `implement-spec`. Ответ на `/oc explain this issue` открыт в [проверенном комментарии](https://github.com/vrmelikadamyan/ai-for-developers-project-387/issues/2#issuecomment-6952378959), а журнал — в [успешном прогоне](https://github.com/vrmelikadamyan/ai-for-developers-project-387/actions/runs/44113628037).

[Workflow OpenCode](.github/workflows/opencode.yml) обрабатывает события `issue_comment` и `pull_request_review_comment` только при создании комментария. Команды доступны доверенным участникам с правом записи. Комментарии ботов и PR из форков пропускаются. Модель `deepseek/deepseek-flash` получает ключ из секрета Actions `DEEPSEEK_API_KEY`. OpenCode отвечает от имени GitHub App в том же обсуждении. Журнал выполнения доступен в [Actions → OpenCode](https://github.com/vrmelikadamyan/ai-for-developers-project-387/actions/workflows/opencode.yml).

Публичная ссылка на сессию отключена (`share: false`; используемая версия OpenCode уже прекратила публикацию сессий). Для одного issue или PR одновременно выполняется один запрос. На работу в issue отводится до 45 минут, на правку PR — до 15 минут. Остановить текущий запуск можно через **Cancel workflow**, отключить новые — через **Disable workflow**.

### Автотриаж новых обращений

Когда доверенный участник с правом записи открывает issue, [Issue triage](.github/workflows/issue-triage.yml) запускает OpenCode с `deepseek/deepseek-flash` без команды `/oc`. Скилл `triage` сверяет обращение с кодом календаря. В комментарии от `github-actions[bot]` появляются рекомендуемые метки, следующий шаг и вопросы, если для решения нужны подробности.

Workflow слушает только `issues.opened`. Для ботов, внешних авторов и тикетов, созданных с меткой `ready-for-agent`, GitHub показывает статус задания `skipped`. Если issue успели закрыть или пометить готовым во время ожидания, агент тоже пропустит его. Автотриаж и интерактивный OpenCode используют общую очередь для каждого issue. Лимит автотриажа — 10 минут. Для чтения репозитория и ответа в issue используются права `contents: read` и `issues: write` токена GitHub Actions. [Прогоны Issue triage](https://github.com/vrmelikadamyan/ai-for-developers-project-387/actions/workflows/issue-triage.yml)

Проверка на `master` подтвердила оба сценария. ### Проверка pull request

Для PR доверенного участника или OpenCode из этого репозитория [проверка PR](.github/workflows/pr-review-request.yml) запускает [независимое ревью](.github/workflows/pr-review.yml). Ревьюер читает diff, [критерии календаря](REVIEW.md), связанные issues, согласование и доступные результаты CI. Замечания и проверенный SHA появляются в обсуждении PR. Автор передаёт подтверждённое замечание командой `/oc` в обсуждении или у строки diff. После нового push ревью повторяется.

На один PR выделены две попытки интерактивной правки, общие для обоих видов комментариев. Повтор запуска через **Re-run** также расходует попытку. Счётчик использует историю запусков Actions и номера попыток. Если во время проверки страницы истории расходятся или содержат не все запуски, проверка один раз перечитывает историю с начала в том же запуске, а при повторном расхождении останавливается с причиной `infra`. У OpenCode App есть право читать историю; менять workflow может владелец или участник с соответствующим доступом. Перед вызовом в PR с правками самого workflow нужно проверить эти изменения. Удаление истории администратором меняет расчёт. При остановке отчёт «нужен человек» содержит SHA и ссылку на журнал. `limit_exhausted` означает исчерпанный бюджет, `timeout` — истёкший лимит времени, `infra` — сбой подготовки, `agent_failed` — ошибку агента.

[Браузерная проверка PR](.github/workflows/pr-browser.yml) поднимает календарь из точного head SHA и сохраняет `booking-browser-<SHA>` в артефактах Actions. В `result.json` указаны ожидаемый и фактический SHA и результат. Трассировки гостя и владельца содержат снимки экрана. Перед слиянием откройте артефакт последнего коммита, проверьте вывод CI и заполните [шаблон PR](.github/pull_request_template.md). Ветка `master` требует успешный `check`.

### Ежедневный аудит календаря

Workflow Scheduled audit использует переменную репозитория `APP_URL`. Сейчас она указывает на публичную страницу записи проекта 386. [Workflow](.github/workflows/scheduled-audit.yml) · [Проверяемое приложение](https://hexlet386-calendar-vrm.onrender.com/book). Расписание — один раз в день, `17 3 * * *`, то есть 06:17 по Москве. Ручной запуск доступен в [Actions → Scheduled audit](https://github.com/vrmelikadamyan/ai-for-developers-project-387/actions/workflows/scheduled-audit.yml) через **Run workflow** на `master`. У задания лимит 25 минут и общая очередь для ручных и плановых запусков.

Обычный шаг сначала пробуждает Render Free запросом `/api/health` с ограниченными повторами, затем запускает Lighthouse 13.6.0 в Chrome. Данные собираются HTTP-запросами чтения и загрузкой страницы в Chrome. Исходные JSON и HTML сохраняются вне Git, в артефакте `lighthouse-report` на 30 дней, в том числе при последующем сбое анализа. Если сам сбор не состоялся, отчёт отсутствует, а причина доступна в Actions.

Скрипт передаёт OpenCode 1.19.6 / `deepseek/deepseek-flash` сводку, содержащую точный URL, баллы категорий, до 20 неуспешных проверок с `auditId`, `score`, `displayValue`, рекомендацией Lighthouse и фрагментом исходных деталей. OpenCode вызывается обычной командой `run --pure --format json`, получает явную инструкцию и выбирает не более одной обоснованной находки или объясняет отсутствие находок. У модели нет инструментов и токена GitHub. Пустой, ошибочный или некорректный JSON-ответ допускает одну повторную попытку; журнал модели и нормализованные данные сохраняются в `audit-analysis`.

Детерминированный публикатор сверяет выбранный `auditId` с отчётом и повторно выполняет `gh issue list --state all`. Для новой находки он создаёт issue с меткой `needs-triage`, проблемой, действием, точным адресом и ссылкой на исходный прогон с отчётом. Постоянный маркер зависит от origin/path страницы и `auditId`; существующее, в том числе закрытое, issue используется повторно. Для проверки повторов учитываются только служебные маркеры в issues и комментариях от GitHub Actions. [Issue #26](https://github.com/vrmelikadamyan/ai-for-developers-project-387/issues/26) служит постоянным журналом, в котором сохраняются итог модели, баллы, результат публикации и отпечаток исходного JSON. При обычной ошибке шаг публикации записывает туда недоступный аудит, без объявления дефекта приложения. При отмене запуска или достижении лимита в 25 минут публикация комментария и сохранение артефактов могут не выполниться. Тогда результат проверяют по статусу запуска в Actions. Workflow получает `contents: read`, `issues: write` и `actions: read` для чтения исходников, публикации результатов и проверки источника повторного отчёта.

Для проверки дублей укажите в поле `source_run_id` номер успешного запуска этого же workflow из `master`. Он скачает сохранённые JSON/HTML того запуска. Одинаковый отпечаток отчёта не создаёт ни issue, ни повторного комментария, даже если модель выберет другую находку. После удаления артефакта повторить его уже нельзя, но сводка и обращения остаются в GitHub. Исправление найденного дефекта требует отдельного решения владельца.

## Docker и деплой

Из корня репозитория соберите образ и запустите его на выбранном порту:

```bash
mise exec -- docker build -t call-calendar .
mise exec -- docker run --rm -e PORT=8090 -p 127.0.0.1:8090:8090 -v calendar-data:/app/data call-calendar
```

Откройте [локальный календарь](http://localhost:8090/). Spring раздаёт собранный React-интерфейс и API на одном порту. Без переменной `PORT` приложение слушает 8080. Именованный том `calendar-data` сохраняет базу H2 при замене локального контейнера.

Для деплоя через Codex:

1. Откройте репозиторий как доверенный проект. Адрес официального Render MCP и идентификатор OAuth-клиента заданы в [проектной конфигурации](.codex/config.toml).
2. Из корня выполните `mise exec -- codex mcp login render` и подтвердите доступ в браузере. Команда `mise exec -- codex mcp list` показывает состояние подключения. Данные сессии хранит Codex вне репозитория. [Подключение Render MCP](https://render.com/docs/mcp-server)
3. В Codex выберите своё пространство Render. Для сервиса используйте **Web Service**, тариф **Free**, среду **Docker**, ветку `master` и корневой `Dockerfile`. Render передаёт `PORT` при запуске. Для проверки откройте `/api/health` и страницу `/book` на адресе сервиса.

**Хранение на Render Free.** Типы встреч и записи хранятся в файле H2 внутри контейнера. При перезапуске на Render, новом деплое или переходе в спящий режим эти данные сбрасываются. После пробуждения список может быть пуст: для новой проверки создайте тип встречи в разделе владельца. [Ограничения Render Free](https://render.com/docs/free#local-files-lost-on-redeploy)

## Сценарий

Владелец календаря один и задан заранее, гость приходит без регистрации. Авторизации и внешних календарей нет.

**Владелец: создание типа встречи**

1. Владелец открывает раздел типов встреч и нажимает «Создать».
2. Заполняет название («Знакомство»), описание («Короткий созвон, чтобы познакомиться») и длительность (30 мин) и сохраняет.
3. Тип встречи появляется в списке и становится доступен гостям.

**Гость: запись на звонок**

4. Гость открывает главную страницу и нажимает «Записаться».
5. Выбирает тип встречи «Знакомство».
6. Видит календарь на ближайшие 14 дней. У каждого дня показано число свободных слотов, дни вне окна записи недоступны.
7. Выбирает дату, например субботу, 28 марта. Справа появляется список слотов по 30 минут (09:00–09:30, 09:30–10:00, …) со статусом «Свободно» или «Занято».
8. Выбирает свободный слот 09:00–09:30 и нажимает «Продолжить».
9. На шаге «Подтверждение записи» вводит имя и email, при желании — тему разговора, и нажимает «Подтвердить запись». Подсказка у поля напоминает, что список предстоящих событий открыт всем.
10. Видит сообщение «Бронь подтверждена. До встречи!» с кнопкой «Забронировать ещё». Если тема указана, она показана в подтверждении. Слот 09:00–09:30 теперь показан как «Занято» для всех типов встреч, а счётчик свободных слотов уменьшается на 1.

**Владелец: просмотр записей**

11. Владелец открывает «Предстоящие события» и видит новую запись: имя и email гостя, тему разговора (если гость её указал), тип встречи, дату и время слота, дату создания. Список открыт всем, поэтому тему видят все посетители. В список попадают предстоящие встречи всех типов, отсортированные по времени.

**Правила бронирования**

- Длительность слота равна длительности типа встречи. Шаг стартов, часы работы и часовой пояс фиксируются в спецификации.
- Одно время нельзя занять дважды, даже разными типами встреч, включая частичное пересечение. Встреча может начаться ровно в момент окончания предыдущей.
- Если два гостя одновременно бронируют один слот, успешной будет только одна запись, второй получит ошибку «слот занят».

## Стек

- **API-контракт:** [TypeSpec](https://typespec.io/) → OpenAPI 3 (`openapi/openapi.yaml`)
- **Бекенд:** Java 25, Spring Boot 4, Maven; серверные интерфейсы и DTO генерирует `openapi-generator`
- **Фронтенд:** TypeScript, React, Vite, Mantine; клиентский SDK генерирует `@hey-api/openapi-ts`
- **Тесты:** JUnit 5 (бекенд), Vitest + Testing Library (фронтенд), Playwright + Chromium (сквозная запись на звонок)
- **Линтеры:** Error Prone + NullAway, Spotless (google-java-format), Oxlint + oxfmt, `tsc`, jactionlint
- **Окружение:** [mise](https://mise.jdx.dev/) (версии инструментов, задачи, daemons), [hk](https://hk.jdx.dev/) (git-хуки)

## Установка

Нужен только [mise](https://mise.jdx.dev/getting-started.html), остальные инструменты и их версии он возьмёт из `mise.toml`.

```bash
git clone https://github.com/vrmelikadamyan/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise trust
mise install
mise run install
```

`mise run install` ставит npm-зависимости и git-хуки (`hk install`).

## Использование

```bash
mise run dev
```

Запускает бекенд (http://localhost:8080) и фронтенд (http://localhost:5173) фоновыми процессами. Остановить: `mise daemons stop backend frontend`.

```bash
mise run check
```

Прогоняет все проверки — линтеры, проверку типов и тесты. Та же команда запускается в GitHub Actions на каждый push.

При первом запуске тестов Playwright скачивает свою версию Chromium. В минимальной установке Ubuntu системные библиотеки для браузера можно поставить командой `mise exec -- pnpm --filter frontend exec playwright install-deps chromium`. Сквозной тест поднимает Spring и Vite на свободных портах, использует временную файловую H2 и проверяет записи с темой разговора и без неё в отдельных сессиях владельца и гостя.

Запустить только этот сценарий после установки зависимостей:

```bash
mise exec -- pnpm --filter frontend exec playwright install --only-shell chromium
mise exec -- sh -c 'cd backend && ./mvnw -B -q test -Dtest=BookingBrowserTest'
```

`mise run api:generate` компилирует TypeSpec в OpenAPI и генерирует интерфейсы и DTO Spring, а также клиентский SDK. После изменения контракта добавьте обновлённые файлы из `openapi/` и `frontend/src/api/generated/` в индекс Git вместе с TypeSpec. Локально и в CI команда `mise run check` сначала сравнивает эти файлы с результатом генерации во временном каталоге.

По умолчанию сервер хранит данные в файловой H2 по пути `./data/calendar` относительно своего рабочего каталога. При запуске через `mise run dev` это `backend/data/`. Переменная `SPRING_DATASOURCE_URL` позволяет выбрать другой файл.

Остальные задачи: `mise tasks`.
